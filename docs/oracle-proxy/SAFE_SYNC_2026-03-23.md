## Why direct full sync is unsafe

The currently deployed oracle-proxy codebase is based on the older TQZHR line and contains local registration customizations. Upstream `chenyme/main` has diverged heavily and includes broad changes across:

- token management
- config/storage layout
- admin API structure
- reverse/grok service internals
- video/function UI routing layout

A direct reset/rebase/merge onto upstream main would risk breaking:

- local registration flow
- solver integration
- email/TOS/birth-date/NSFW registration steps
- token persistence/loading
- current production container behavior

## Safe-sync policy

Prefer only these categories for incremental adoption:

1. isolated feature additions in API/UI layers that do not alter token persistence or registration flow
2. logging improvements that can be enabled conservatively
3. documentation or test updates
4. narrowly-scoped bug fixes with clear blast radius

Avoid for now:

1. token manager/storage rewrites
2. config schema migrations
3. wholesale route/layout refactors from `_public/` structure into new function/admin page trees
4. bulk reverse service rewrites
5. any change that assumes the newer upstream directory structure already exists locally
